# L2 - Detailed Requirements

Each L2 traces to exactly one L1 in `L1.md`. Acceptance criteria are written in
Given/When/Then form and are the source for the acceptance tests required by
`AGENTS.md`. Every acceptance test must carry a `Traces to:` comment naming the L2
requirements it covers.

**Programme shape, authored and binding on everything below:** a cohort follows exactly
one programme and takes its modules one per week, with a 1-on-1 session at the cohort's
own cadence. The module count comes from the authored programme; the duration, the
cadence, and the session allowance that follows from them come from the cohort record.
None of those figures is a constant. Modules unlock sequentially. A participant holds at
most one open booking. Bookings are changeable or cancellable until 24 hours before the
start.

Worked examples below use a 12-module programme and a 12-week cohort with a fortnightly
cadence, giving an allowance of 6 sessions. Those figures illustrate the rules; they do
not fix them.

Viewport breakpoints referenced throughout: XS `<576px`, SM `>=576px`, MD `>=768px`,
LG `>=992px`, XL `>=1200px`.

---

## L2-001: Sign in with an email address and password
**Traces to:** L1-001

A participant must present a registered email address and password to obtain an
authenticated session. Failed attempts must not reveal whether the email address is
registered.

**Acceptance Criteria:**
1. Given a registered participant, when they submit their correct email address and password, then the system establishes an authenticated session and shows the curriculum.
2. Given a registered participant, when they submit a correct email address and an incorrect password, then the system refuses access and displays the message "Email address or password is incorrect".
3. Given an email address that is not registered, when it is submitted with any password, then the system displays the identical message "Email address or password is incorrect" and takes no less time to respond than a failure for a registered address.
4. Given an empty email address or an empty password, when the form is submitted, then the system refuses submission and marks the empty field.

---

## L2-002: Maintain and expire an authenticated session
**Traces to:** L1-001

An authenticated session must survive browser restarts for a bounded lifetime and must
end on expiry.

**Acceptance Criteria:**
1. Given an authenticated participant, when they close the browser and return within 14 days, then they reach the curriculum without signing in again.
2. Given an authenticated participant whose session has been idle for 30 days, when they request any screen, then the system requires them to sign in again.
3. Given a session that has expired, when the client calls any API endpoint, then the API responds 401 and returns no programme data.

---

## L2-003: Sign out
**Traces to:** L1-001

A participant must be able to end their session deliberately from the device in use.

**Acceptance Criteria:**
1. Given an authenticated participant, when they sign out, then the system ends the session and shows the sign-in screen.
2. Given a participant who has signed out, when they use the browser back button, then no programme content is displayed and the sign-in screen is shown.
3. Given a participant signed in on two devices, when they sign out on one, then the session on the other device remains valid.

---

## L2-004: Refuse programme content to unidentified visitors
**Traces to:** L1-001

Every participant-facing route and every programme API endpoint must require an
authenticated session.

**Acceptance Criteria:**
1. Given an unauthenticated visitor, when they request the curriculum, a module, the sessions screen, or notes by direct URL, then the system redirects to sign-in and displays no programme content.
2. Given an unauthenticated client, when it calls any programme API endpoint, then the API responds 401.
3. Given an unauthenticated visitor who is redirected from a deep link, when they sign in successfully, then the system takes them to the screen they originally requested.

---

## L2-005: A participant belongs to exactly one cohort
**Traces to:** L1-002

Enrollment places a participant in exactly one cohort, which supplies their curriculum,
programme dates, session cadence, and mentor.

**Acceptance Criteria:**
1. Given an enrolled participant, when they open the curriculum, then the modules, week number, cohort end date, and mentor name shown are those of their cohort.
2. Given an enrolled participant, when the system resolves any programme data for them, then data belonging to another cohort is never returned.
3. Given a participant record, when enrollment is inspected, then exactly one active cohort is associated with it.

---

## L2-006: A cohort defines duration, cadence, and mentor
**Traces to:** L1-002

A cohort carries a start date, an authored duration in weeks, an authored session
cadence in weeks, and exactly one mentor. The duration and the cadence are properties of
the cohort record, not constants.

**Acceptance Criteria:**
1. Given a cohort with a start date, when the current week is calculated, then it equals the number of whole weeks since the start date plus one, and is capped at that cohort's own authored duration.
2. Given a cohort of 12 weeks with a fortnightly cadence, when its session allowance is calculated, then it equals 6; and given a cohort of 8 weeks with the same cadence, then it equals 4.
3. Given a cohort past its end date, when a participant opens the curriculum, then completed modules remain readable and no new session can be booked.
4. Given a cohort, when its end date is calculated, then it equals its start date advanced by its own authored duration.

---

## L2-007: State the absence of a cohort explicitly
**Traces to:** L1-002

A participant not yet in a cohort must be told so, not shown an empty programme.

**Acceptance Criteria:**
1. Given an authenticated participant with no cohort, when they open the curriculum, then the system displays an explicit message that they are not yet enrolled and shows no module path, progress figures, or booking panel.
2. Given a participant with no cohort, when they request a module or the sessions screen by direct URL, then the system shows the same not-enrolled message rather than an error.

---

## L2-008: Present the curriculum as an ordered path with per-module state
**Traces to:** L1-003

The curriculum path shows every published module of the participant's programme in
order, each in exactly one of three states: complete, current, or locked.

**Acceptance Criteria:**
1. Given an enrolled participant, when they open the curriculum, then one marker is displayed for every published module of their programme, in ascending order, numbered from 01.
2. Given a participant who has completed modules 1 and 2, when they open the curriculum, then modules 1 and 2 render as complete, module 3 renders as current, and every module after the third renders as locked.
3. Given any module marker, when its state is inspected, then it carries exactly one of the three states and its state is available as text, not by colour alone.
4. Given a participant who has completed every module of their programme, when they open the curriculum, then every marker renders as complete and no marker renders as current.

---

## L2-009: Derive every progress figure from recorded completion
**Traces to:** L1-003

Counts, remainders, and proportions displayed about progress must be computed from
completion records against the module count of the participant's programme. No progress
figure is authored as content.

**Acceptance Criteria:**
1. Given a participant with 2 modules complete in a programme of 12, when the curriculum is displayed, then the completed count reads "2 of 12 complete" and the remaining count reads "10 modules remain".
2. Given a participant who completes one further module, when the curriculum is redisplayed without any content change, then the completed count reads 3 and the remaining count reads 9.
3. Given a participant with 0 modules complete in a programme of 8, when the curriculum is displayed, then the completed count reads "0 of 8 complete" and the remaining count reads "8 modules remain".
4. Given any displayed progress proportion, when it is compared with the underlying completion records, then it equals completed divided by total, expressed as a whole percentage.

---

## L2-010: Unlock modules sequentially
**Traces to:** L1-003

Module N+1 becomes available when module N is complete. Module 1 is available on
enrollment.

**Acceptance Criteria:**
1. Given a newly enrolled participant, when they open the curriculum, then module 1 is available and every module after the first is locked.
2. Given a participant whose current module is 3, when they request module 4 by direct URL, then the system refuses access and returns them to the curriculum with an explanation.
3. Given a participant whose current module is 3, when they complete module 3, then module 4 becomes available and becomes the current module.
4. Given a participant whose current module is 3, when they request module 2 by direct URL, then module 2 opens in a readable state, because completed modules remain accessible.

---

## L2-011: Resume the current module where the participant stopped
**Traces to:** L1-003

The curriculum's primary action continues the current module at the first incomplete
section.

**Acceptance Criteria:**
1. Given a participant whose current module has sections 1 and 2 complete, when they activate the continue action, then the module opens at section 3.
2. Given a participant who has not opened their current module, when they activate the continue action, then the module opens at section 1.
3. Given a participant whose current module has every section complete but is not yet marked complete, when they activate the continue action, then the module opens at its last section.

---

## L2-012: Deliver a module as an ordered set of sections
**Traces to:** L1-004

A module presents its sections in order, showing which are complete, which is current,
and the title of each.

**Acceptance Criteria:**
1. Given a participant opening a module, when the module renders, then its section list displays every section in ascending order with its title.
2. Given a module with 5 sections of which 1 is complete, when the module renders, then section 1 shows as complete, section 2 shows as current, and sections 3 through 5 show as not started.
3. Given a participant viewing a section, when the section renders, then its reading content and its practice assignment are both present.

---

## L2-013: Record section completion
**Traces to:** L1-004

A participant marks a section complete, and that record persists.

**Acceptance Criteria:**
1. Given a participant viewing an incomplete section, when they mark it complete, then the section is recorded as complete and the next section becomes current.
2. Given a participant who has marked a section complete, when they leave the application and return, then the section remains complete.
3. Given a participant viewing the final section of a module, when they mark it complete, then the module is recorded as complete and the participant is returned to the curriculum.
4. Given a section already complete, when the participant views it, then the completion action is not offered a second time.

---

## L2-014: Derive the section progress indicator
**Traces to:** L1-004

The module's progress indicator reflects sections completed over sections total.

**Acceptance Criteria:**
1. Given a module of 5 sections with 2 complete, when the module renders, then the progress indicator fills 40% and the label reads "Section 3 of 5".
2. Given a module of 5 sections with 0 complete, when the module renders, then the progress indicator fills 0% and the label reads "Section 1 of 5".
3. Given a module of 5 sections with 5 complete, when the module renders, then the progress indicator fills 100%.
4. Given any module, when the progress indicator is compared with the section records, then its fill equals sections complete divided by sections total.

---

## L2-015: Serve identical assignment content at every viewport
**Traces to:** L1-004

The reading content and the practice assignment of a section are the same for a given
participant regardless of device or viewport size.

**Acceptance Criteria:**
1. Given a practice assignment of 3 steps, when the section is viewed at XS and again at XL, then all 3 steps are present at both sizes.
2. Given a section viewed at XS, when its text content is compared with the same section at XL, then the two are identical.
3. Given a section carrying a stated effort estimate, when it is viewed at any viewport, then the estimate describes the same assignment shown alongside it.

---

## L2-016: Complete a module when all its sections are complete
**Traces to:** L1-004

Module completion is derived from section completion, never set independently.

**Acceptance Criteria:**
1. Given a module with one section incomplete, when module state is resolved, then the module is not complete.
2. Given a module whose every section is complete, when module state is resolved, then the module is complete.
3. Given a module recorded as complete, when a new section is added to it by curriculum change, then the module ceases to be complete until the new section is completed.

---

## L2-017: Show the mentor's open times with per-slot state
**Traces to:** L1-005

The booking panel shows a day strip and the time slots for the selected day, each slot
in exactly one of three states: open, taken, or selected.

**Acceptance Criteria:**
1. Given a participant opening the sessions screen, when the panel renders, then the days of the current booking week are shown and one day is selected.
2. Given a selected day, when its slots render, then every slot the mentor has published for that day is shown, and each is marked open, taken, or selected.
3. Given a slot already booked by another participant, when it renders, then it is marked taken, is not selectable, and reveals nothing about who booked it.
4. Given a participant selecting a different day, when the day changes, then the slots shown are those of the newly selected day.

---

## L2-018: Book an open slot
**Traces to:** L1-005

Confirming a selected open slot creates a session for the participant with their
cohort's mentor.

**Acceptance Criteria:**
1. Given a participant with no open booking who has selected an open slot, when they confirm, then a session is created at that date and time with their mentor and the screen shows it as their next session.
2. Given a newly created session, when the curriculum is opened, then the same date, time, mentor name, and duration are displayed there.
3. Given a participant who has not selected a slot, when they attempt to confirm, then the system takes no action and the confirm action is unavailable.

---

## L2-019: Hold at most one open booking
**Traces to:** L1-005

A participant has at most one future session at a time. While one is held, the panel
offers change and cancellation rather than a further booking.

**Acceptance Criteria:**
1. Given a participant holding a future session, when they open the sessions screen, then the held session is displayed with actions to reschedule and to cancel, and no confirm-booking action is offered.
2. Given a participant holding a future session, when they attempt to book a second slot by direct API call, then the request is rejected and the held session is unchanged.
3. Given a participant whose only future session has passed, when they open the sessions screen, then the booking panel offers slots to book again.
4. Given a participant who cancels their held session, when the screen refreshes, then the booking panel offers slots to book again.

---

## L2-020: Reschedule until 24 hours before the start
**Traces to:** L1-005

A held session moves to another open slot while more than 24 hours remain before its
start.

**Acceptance Criteria:**
1. Given a session starting in more than 24 hours, when the participant selects another open slot and confirms the change, then the session moves to the new slot and the previous slot becomes open.
2. Given a session starting in 24 hours or less, when the participant opens the sessions screen, then the reschedule action is unavailable and the reason is stated.
3. Given a session starting in 23 hours, when a reschedule is attempted by direct API call, then the request is rejected and the session is unchanged.
4. Given a session starting in exactly 24 hours and 1 minute, when a reschedule is attempted, then it succeeds.

---

## L2-021: Cancel until 24 hours before the start
**Traces to:** L1-005

Cancellation follows the same window as rescheduling and returns the slot to the
mentor's availability.

**Acceptance Criteria:**
1. Given a session starting in more than 24 hours, when the participant cancels it, then the session is removed from their upcoming sessions and its slot becomes open to others.
2. Given a session starting in 24 hours or less, when the participant opens the sessions screen, then the cancel action is unavailable and the reason is stated.
3. Given a cancelled session, when the participant's session allowance is recalculated, then the cancelled session does not count against the cohort's allowance.

---

## L2-022: Show the record of sessions held
**Traces to:** L1-005

Past sessions are listed with their date, the module they accompanied, and a route to
their notes.

**Acceptance Criteria:**
1. Given a participant who has held 2 sessions, when they open the sessions screen, then both are listed with date, time, and the module current at the time of the session, most recent first.
2. Given a past session with notes, when the participant activates its notes action, then those notes open.
3. Given a participant who has held no sessions, when they open the sessions screen, then an explicit empty state is shown in place of the list.
4. Given a listed session, when its date is displayed, then a past session is never presented with a date later than the current date.

---

## L2-023: Derive the session allowance from cohort duration and cadence
**Traces to:** L1-005

The number of sessions a cohort includes is computed from the cohort's own authored
duration and cadence, never from a constant: a 12-week cohort at one session every other
week yields 6.

**Acceptance Criteria:**
1. Given a 12-week cohort with a fortnightly cadence, when the allowance is displayed, then it reads 6 and the booked count is expressed against 6; and given an 8-week cohort with the same cadence, then it reads 4 and the booked count is expressed against 4.
2. Given a participant in a 12-week cohort with a fortnightly cadence who has held 2 sessions and holds 1 future session, when the allowance is displayed, then it reads "3 of 6 booked".
3. Given a participant who has used every session their cohort allows, when they open the sessions screen, then no further booking is offered and the exhausted allowance is stated.
4. Given any displayed allowance figure, when compared with the cohort's duration and cadence, then the denominator equals weeks divided by cadence.

---

## L2-024: Refuse a slot taken between display and confirmation
**Traces to:** L1-005

Two participants racing for one slot must not both obtain it.

**Acceptance Criteria:**
1. Given two participants viewing the same open slot, when both confirm and the first succeeds, then the second receives a rejection stating the slot is no longer available.
2. Given a rejected booking, when the panel refreshes, then the contested slot renders as taken and no session was created for the second participant.
3. Given a rejected booking, when the second participant's held-session state is inspected, then it is unchanged.

---

## L2-025: Write and revise a note
**Traces to:** L1-006

A participant creates and edits notes, and revisions persist.

**Acceptance Criteria:**
1. Given a participant viewing a module, when they add a note and save it, then the note is stored and displayed against that module.
2. Given an existing note, when the participant edits and saves it, then the revised text replaces the previous text and the revision time is recorded.
3. Given a note being composed, when the participant navigates away without saving, then they are warned that unsaved text will be lost.
4. Given an empty note body, when a save is attempted, then no note is created.

---

## L2-026: Attach every note to a module or a session
**Traces to:** L1-006

Notes are retrievable both in the place they were written and from a single notes
destination.

**Acceptance Criteria:**
1. Given notes written against modules and sessions, when the participant opens the notes destination, then all their notes are listed with the module or session each belongs to, most recent first.
2. Given a note attached to a module, when that module is opened, then the note is shown with it.
3. Given a participant with no notes, when they open the notes destination, then an explicit empty state is shown.

---

## L2-027: Carry preparation prompts to the session they inform
**Traces to:** L1-006

A module's preparation prompts appear against the session that follows it.

**Acceptance Criteria:**
1. Given a module carrying preparation prompts, when the participant opens their next session, then those prompts are displayed with it.
2. Given a participant who has answered a prompt in a note, when the session is opened, then the answer is displayed beneath the prompt it answers.
3. Given a module with no preparation prompts, when the next session is opened, then no empty prompt area is rendered.

---

## L2-028: Keep notes private to the participant and their mentor
**Traces to:** L1-006

No other participant reaches a participant's notes.

**Acceptance Criteria:**
1. Given a note belonging to participant A, when participant B requests it by its identifier, then the API responds 404 and returns no note content.
2. Given a note belonging to participant A, when A's cohort mentor requests it, then it is returned.
3. Given a note belonging to participant A, when a mentor of a different cohort requests it, then the API responds 404.

---

## L2-029: Present every screen usably from XS to XL
**Traces to:** L1-007

Layouts adapt across the breakpoints without loss of content or horizontal scrolling of
the page body.

**Acceptance Criteria:**
1. Given the curriculum screen at XS, when it renders, then it is a single column, the module path remains legible, and the page body does not scroll horizontally.
2. Given the module screen at XS, when it renders, then the reading content, the practice assignment, and the preparation prompts are all reachable by vertical scrolling.
3. Given the sessions screen at XS, when it renders, then the day strip and the slot grid are both usable without horizontal scrolling of the page body.
4. Given any participant-facing screen at MD, LG, and XL, when it renders, then no content is clipped and no action is obscured.
5. Given any screen at any breakpoint, when a primary action exists, then it is reachable without horizontal scrolling.

---

## L2-030: Offer every destination at every viewport
**Traces to:** L1-007

Curriculum, Sessions, and Notes are reachable at XS as they are at XL.

**Acceptance Criteria:**
1. Given the application at XS, when the participant opens the navigation, then Curriculum, Sessions, and Notes are all offered.
2. Given the application at XS on a module screen, when the participant uses the back affordance, then they return to the curriculum.
3. Given the set of destinations available at XL, when it is compared with the set available at XS, then the two sets are identical.

## L2-031: Meet contrast minimums
**Traces to:** L1-008

Text and meaningful non-text marks meet WCAG 2.1 AA contrast against their background.

**Acceptance Criteria:**
1. Given any text below 18.66px regular or 14px bold, when its contrast against its background is measured, then the ratio is at least 4.5:1.
2. Given any larger text, when its contrast is measured, then the ratio is at least 3:1.
3. Given a module path marker, a slot state, or any other non-text mark that carries meaning, when its contrast against its background is measured, then the ratio is at least 3:1.
4. Given the complete and the locked states of a module path marker, when they are compared, then they are distinguishable by a means other than lightness alone.

---

## L2-032: Meet minimum target size
**Traces to:** L1-008

Every interactive target is large enough to hit reliably on a touch screen.

**Acceptance Criteria:**
1. Given any interactive element on any screen, when its hit area is measured, then it is at least 44px by 44px.
2. Given two adjacent interactive elements, when the gap between their hit areas is measured, then the hit areas do not overlap.
3. Given a text link inside a paragraph of running prose, when its hit area is measured, then it is exempt from the 44px minimum, because it is an inline link within text.

---

## L2-033: Operate by keyboard
**Traces to:** L1-008

Every action is reachable and operable without a pointing device.

**Acceptance Criteria:**
1. Given any screen, when the participant traverses it with the Tab key, then every interactive element receives focus in the order it appears on screen.
2. Given a focused element, when it renders, then a visible focus indicator distinguishes it from unfocused elements at a contrast of at least 3:1.
3. Given a dialog, when it opens, then focus moves into it, remains within it, and returns to the triggering element when it closes.
4. Given any action available by pointer, when it is attempted by keyboard alone, then it completes.

## L2-034: Convey state by more than colour
**Traces to:** L1-008

Module state, section state, and slot state are each available in text or shape.

**Acceptance Criteria:**
1. Given a module path marker, when it is read by a screen reader, then its state is announced as complete, current, or locked.
2. Given a time slot marked taken, when it is read by a screen reader, then its unavailability is announced.
3. Given the interface rendered in greyscale, when a participant inspects module and slot states, then each remains distinguishable.

## L2-035: Authorise every request against the requesting participant
**Traces to:** L1-009

Identity from the session, never from the request body, determines what data is
returned. A participant reaches only their own data.

**Acceptance Criteria:**
1. Given participant A's session, when a request supplies participant B's identifier, then the response contains only A's data or a 404, and never B's data.
2. Given a request for a module outside the requesting participant's cohort, when it is served, then the API responds 404.
3. Given a request to modify a session booking that belongs to another participant, when it is served, then the API responds 404 and the booking is unchanged.
4. Given any programme endpoint, when it resolves the acting participant, then it derives that identity from the authenticated session alone.

---

## L2-036: Validate every input at the boundary
**Traces to:** L1-009

The API rejects malformed, oversized, and unexpected input before it reaches domain
logic.

**Acceptance Criteria:**
1. Given a request with a missing or malformed required field, when it is submitted, then the API responds 400 with a message naming the invalid field and no state changes.
2. Given a note body exceeding its maximum length, when it is submitted, then the API responds 400 and no note is stored.
3. Given note text containing HTML or script markup, when it is stored and later displayed, then it renders as literal text and no markup executes.
4. Given a request body carrying fields the endpoint does not define, when it is submitted, then those fields are ignored and cannot alter stored state.

---

## L2-037: Protect credentials and data in transit and at rest
**Traces to:** L1-009

**Acceptance Criteria:**
1. Given any request over plain HTTP, when it reaches the application, then it is redirected to HTTPS.
2. Given a stored password, when the store is inspected, then it holds a salted one-way hash from a current password-hashing algorithm and never the password itself.
3. Given a session cookie, when it is issued, then it carries the HttpOnly, Secure, and SameSite attributes.
4. Given an application error, when its message reaches the client, then the message contains no stack trace, connection string, or internal identifier.

---

## L2-038: Limit repeated sign-in attempts
**Traces to:** L1-009

Credential guessing is slowed at the account and the origin.

**Acceptance Criteria:**
1. Given 10 failed sign-in attempts for one email address within 15 minutes, when an eleventh is made, then it is refused for a stated cooling-off period regardless of whether the password is correct.
2. Given a refused attempt during cooling-off, when the response is inspected, then it does not disclose whether the submitted password was correct.
3. Given a participant in cooling-off, when the period elapses, then a correct password is accepted again.
4. Given repeated failures, when they are refused, then each is recorded with its timestamp and originating address.

---

## L2-039: Respond within stated budgets
**Traces to:** L1-010

**Acceptance Criteria:**
1. Given a read endpoint under normal load, when response time is measured over 100 requests, then the 95th percentile is at most 300ms.
2. Given a write endpoint under normal load, when response time is measured over 100 requests, then the 95th percentile is at most 500ms.
3. Given the curriculum screen on a mid-tier device over a 4G connection, when it is loaded, then it becomes interactive within 2.5 seconds.
4. Given any screen, when its transferred payload is measured, then it does not exceed 300KB compressed, excluding module media.

---

## L2-040: Emit operational signals
**Traces to:** L1-010

The system reports its own health and records what happened.

**Acceptance Criteria:**
1. Given the API is running, when a health endpoint is requested, then it responds 200 with the status of the application and its data store.
2. Given the data store is unreachable, when the health endpoint is requested, then it responds 503 and names the failing dependency.
3. Given an unhandled error, when it occurs, then it is logged with a correlation identifier, and the same identifier is returned to the client.
4. Given a booking is created, changed, or cancelled, when the action completes, then it is recorded with the acting participant, the action, and the time.

---

## L2-041: Report administrator authority on the session
**Traces to:** L1-011

An account either holds administrator authority or it does not, and the authenticated
session must report which. Authority is resolved from the session alone.

**Acceptance Criteria:**
1. Given an administrator account, when the session is requested, then the response states that the account holds administrator authority.
2. Given a participant account without administrator authority, when the session is requested, then the response states that the account does not hold it.
3. Given a request supplying an administrator flag in its body, query string, or headers, when it is served, then the supplied value is ignored and authority is resolved from the session.
4. Given an unauthenticated visitor, when the session is requested, then the API responds 401 and states no authority.

---

## L2-042: Admit only administrators to the authoring screens
**Traces to:** L1-011

Every authoring screen requires administrator authority, whether reached by navigation
or by direct URL.

**Acceptance Criteria:**
1. Given an administrator, when they open the curriculum authoring screens, then the screens render.
2. Given a signed-in participant without administrator authority, when they request an authoring screen by direct URL, then no authoring content is displayed and they are returned to the curriculum with an explanation.
3. Given an unauthenticated visitor, when they request an authoring screen by direct URL, then they are redirected to sign-in and no authoring content is displayed.
4. Given a participant without administrator authority, when the navigation renders, then no authoring destination is offered.
5. Given an administrator redirected from an authoring deep link to sign in, when they sign in successfully, then they are taken to the authoring screen they originally requested.

---

## L2-043: Refuse every authoring request that lacks administrator authority
**Traces to:** L1-011

The API refuses authoring calls from participants and from unauthenticated clients, and
refuses them before any change is made.

**Acceptance Criteria:**
1. Given an unauthenticated client, when it calls any authoring endpoint, then the API responds 401 and returns and changes no curriculum data.
2. Given a signed-in participant without administrator authority, when they call any authoring endpoint, then the API responds 403 and returns and changes no curriculum data.
3. Given a refused authoring call, when the stored curriculum is inspected, then it is unchanged.
4. Given an administrator whose session has expired, when they call an authoring endpoint, then the API responds 401.

## L2-044: Create and revise a programme
**Traces to:** L1-012

A programme is the unit a cohort follows. An administrator creates it, titles it, and
gives it a key unique across programmes.

**Acceptance Criteria:**
1. Given an administrator on the programmes screen, when they create a programme with a key and a title, then the programme is stored and appears in the programme list.
2. Given a programme key already in use, when a second programme is created with that key, then the creation is refused, the reason states that the key is taken, and nothing is stored.
3. Given an administrator with no programmes, when they open the programmes screen, then an explicit empty state is shown in place of the list.
4. Given a stored programme, when the administrator revises its title, then the new title is stored and displayed on the next render.

## L2-045: Create, revise, and remove a module
**Traces to:** L1-012

Modules are created within a programme, carry a title and a summary, and are removable
while nothing recorded depends on them.

**Acceptance Criteria:**

2. Given a stored module, when the administrator revises its title or summary, then the revision is stored and displayed on the next render.
3. Given a module no participant has recorded completion against, when the administrator removes it, then the module and its sections and prompts are removed and the remaining modules keep a contiguous order.
4. Given a programme with no modules, when it is opened for authoring, then an explicit empty state invites the first module.

Each module carries an effort estimate and an ordered list of practice steps, both

2. Given a module with practice steps, when the administrator reorders them, then participants read them in the new order.
3. Given a module with practice steps, when the administrator removes one, then it no longer appears and the remaining steps keep a contiguous order.
4. Given a module with no practice steps, when a participant reads it, then no empty practice area is rendered.

## L2-049: Order modules and sections
**Traces to:** L1-012

Order is authored, and every position within a programme and within a module is unique
and contiguous.

**Acceptance Criteria:**

2. Given a module whose sections occupy positions 1 through 5, when the administrator moves the first section to the last position, then participants read the sections in the new order.
3. Given a reorder that fails before it completes, when the stored order is inspected, then it is the order that held before the reorder began.
4. Given any programme or module, when its stored order is inspected, then no two children share a position and the positions run from 1 without a gap.

## L2-050: Refuse a removal that would discard recorded completion
**Traces to:** L1-012

Recorded participant history outranks authoring convenience. Content a participant has
completed or answered cannot be deleted out from under that record.

**Acceptance Criteria:**
1. Given a section at least one participant has marked complete, when the administrator attempts to remove it, then the removal is refused, the reason names the recorded completion, and the section remains.
2. Given a module containing a section at least one participant has completed, when the administrator attempts to remove the module, then the removal is refused and the module remains.
3. Given a preparation prompt a participant has answered in a note, when the administrator attempts to remove it, then the removal is refused and the prompt remains.
4. Given a refused removal, when the affected participant next opens the curriculum, then their recorded progress is unchanged.

## L2-051: Validate every authored field at the boundary
**Traces to:** L1-012

Authored content is checked before it reaches domain logic, and a rejected edit changes
nothing.

**Acceptance Criteria:**
1. Given an authoring request with an empty required field, when it is submitted, then the API responds 400 with a message naming the field and stores nothing.
2. Given an authored title longer than its stated maximum, when it is submitted, then the API responds 400 and stores nothing.

4. Given an authoring request naming a programme, module, section, or prompt that does not exist, when it is submitted, then the API responds 404 and stores nothing.
5. Given an authoring request carrying fields the endpoint does not define, when it is submitted, then those fields are ignored and cannot alter stored state.

A programme and each of its modules carry a publication state. Newly created content is
